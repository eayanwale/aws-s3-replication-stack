# v1.17 — Presentation Cleanup

**Date:** 2026-06-14

---

## What Was Cut

The stack had grown to cover seven distinct S3 features (encryption, website hosting, event notifications, CloudTrail data events, object uploads, replication, lifecycle). For a presentation focused on **cross-region + cross-account replication**, most of that was noise. This pass strips the stack down to the replication story and the security baseline that supports it.

| Removed | Why |
|---|---|
| `cloudtrail.tf` | CloudTrail data events are a separate topic. They added a third bucket, its own bucket policy, and an `aws_cloudtrail` resource that wasn't part of the demo. |
| `website.tf` | Static website hosting is unrelated to replication. The bucket no longer needs to be a website endpoint. |
| `notifications.tf` | SNS topic with no subscribers. Dead weight. |
| `objects.tf` + `assets/` directory | Terraform-managed file uploads are a demo-only pattern. Removing them eliminates the file dependency and the `index.html`/`error.html` website artifacts. |
| `outputs.tf` | Grep confirmed no other stack consumed any of the exposed values. |
| `encryption.tf` | Customer-managed KMS encryption was creating more problems than it solved (see "KMS Removal" below). |

## What Was Fixed

Several existing bugs surfaced during cleanup and were resolved as side effects:

| File | Bug | Fix |
|---|---|---|
| `replica_account.tf` | The cross-account replica bucket was configured with `kms_master_key_id = aws_kms_key.bucket_key.id`, a KMS key that lives in the **source** account. The destination account can't see it, so this would have failed at apply or broken replication. | Switched the destination to SSE-S3. The reference disappeared along with KMS. |
| `replica_account.tf`, `replica_region.tf` | Both replica buckets had `object_lock_enabled = true` but no corresponding `aws_s3_bucket_object_lock_configuration`. The capability was turned on with no rules. | Dropped the flag from both. |
| `replica_region.tf` | A bucket policy was granting the source-account replication role write access to the **same-account** region replica. For same-account replication this is redundant — the IAM role already has the perms. | Deleted the bucket policy. |
| `replication.tf` | The `depends_on` block on `aws_s3_bucket_replication_configuration` listed ten resources, most of which Terraform already infers from the resource references in the config body. | Removed the entire `depends_on` block. |
| `security.tf` | `block_public_policy` and `restrict_public_buckets` were set to `false` so the public website-serving policy in `policies.tf` could land. | Flipped both to `true` once the website was gone. All four public-access flags are now `true`. |
| `policies.tf` | The main bucket had a policy granting `s3:GetObject` to `Principal: "*"` — a public-read policy that only existed because of the website. | Deleted. The main bucket no longer has a bucket policy. |

## KMS Removal

The decision to drop KMS deserves its own note. The previous setup had three KMS keys:

1. `aws_kms_key.bucket_key` — customer-managed CMK for the main bucket in `us-east-1`
2. `aws_kms_key.region_replication_key` — separate CMK for the region replica in `us-east-2` (KMS keys are region-scoped, so cross-region replication needs one per region)
3. The cross-account replica was *trying* to use key #1, which was the bug above

KMS encryption is a real production concern, but for a replication demo it adds:
- Two KMS keys + their resource policies + the `kms:Decrypt` and `kms:Encrypt`/`GenerateDataKey` grants on the replication role
- `source_selection_criteria { sse_kms_encrypted_objects { ... } }` on the replication config (only needed when the source is KMS-encrypted)
- An `encryption_configuration { replica_kms_key_id = ... }` block per destination
- The cross-account complexity of providing a destination-account-owned KMS key

Switching to SSE-S3 (AES256) removes ~70 lines, 5 resources, the cross-account KMS bug, and a layer of explanation that doesn't serve the replication story. Encryption at rest is still on — AWS applies SSE-S3 by default to every new bucket created since January 2023.

## What's Kept

The stack now has 11 `.tf` files:

| File | What |
|---|---|
| `main.tf` | Main bucket + logging bucket |
| `security.tf` | Public-access block, versioning, object lock config |
| `lifecycle.tf` | Glacier transition + noncurrent version expiry |
| `logging.tf` | S3 server access logging into the logging bucket |
| `policies.tf` | Logging bucket policy (only) |
| `replication.tf` | Replication IAM role + policy + two-rule replication config |
| `replica_region.tf` | Region replica bucket in `us-east-2` |
| `replica_account.tf` | Account replica bucket in `REPLICA_ACCOUNT_ID` |
| `provider.tf` | Three AWS providers (default, `us-east-2`, `test-account`) |
| `vars.tf` + `terraform.tfvars` | Variables |
| `versions.tf` | Terraform/provider version pins |

Both replication paths — cross-region (same account) and cross-account (different account) — are preserved. They're the centerpiece of the presentation.

## Diff Summary

- 4 files deleted (`cloudtrail.tf`, `website.tf`, `notifications.tf`, `objects.tf`, plus the `assets/` directory)
- 2 files deleted as part of KMS removal-adjacent cleanup (`encryption.tf`, `outputs.tf`)
- 6 files trimmed (`main.tf`, `security.tf`, `policies.tf`, `replication.tf`, `replica_region.tf`, `replica_account.tf`)
- 1 file rewritten (`docs/STACK-S3.md`)
