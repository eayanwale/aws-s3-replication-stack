# v1.4–v1.8 — Security Hardening Series

**Branches:** `STC15-1391_Block_Public_Access_v1.4` through `STC15-1395_Configure_Server_Access_Logging_v1.8`
**Period:** 2026

This was a sequential hardening pass — each PR added one security layer to the bucket.

---

## v1.4 — Block Public Access (STC15-1391)

Added `aws_s3_bucket_public_access_block` with all four settings enabled:

```hcl
block_public_acls       = true
block_public_policy     = true
ignore_public_acls      = true
restrict_public_buckets = true
```

**Why:** S3 has had well-publicized data breaches caused by misconfigured public ACLs or overly permissive bucket policies. Enabling all four block settings at the bucket level provides a hard stop regardless of what ACLs or policies are applied later — even if a future policy accidentally allows public access, the block override prevents it.

---

## v1.5 — Versioning (STC15-1392)

Added `aws_s3_bucket_versioning` with `status = "Enabled"`.

**Why:** Versioning retains all object versions, including deleted objects (as delete markers). This enables:
- Recovery from accidental deletes (remove the delete marker)
- Recovery from overwrites (restore a previous version)
- Required prerequisite for Object Lock (added in v1.13) and Cross-Region Replication (added in v1.11)

**Trade-off:** Versioning increases storage costs because every version is billed. Lifecycle rules (v1.10) are used to expire old versions and control this.

---

## v1.6 — AES256 Encryption (STC15-1393)

Added `aws_s3_bucket_server_side_encryption_configuration` using `AES256` (SSE-S3 — AWS-managed keys).

**Why AES256 first:** SSE-S3 requires no additional infrastructure — AWS manages the key rotation. It satisfies basic encryption-at-rest requirements and was chosen as the first step before introducing customer-managed KMS keys in v1.7.

---

## v1.7 — KMS Encryption (STC15-1394)

Upgraded from AES256 to a customer-managed KMS key (`aws_kms_key`).

**Why upgrade to KMS:**
- KMS key rotation can be enabled (automatic annual rotation)
- Key usage is logged in CloudTrail — every encryption/decryption event is auditable
- The key can be disabled or deleted to revoke access to all encrypted objects
- Required for cross-account replication where the destination account needs explicit KMS grants (see v1.12)

---

## v1.8 — Server Access Logging (STC15-1395)

Added `aws_s3_bucket_logging` to write S3 access logs to a separate logging bucket.

**What's logged:** Every request to the bucket — `GET`, `PUT`, `DELETE`, `LIST` — is recorded with timestamp, requester identity, request URI, and response code.

**Why a separate bucket:** Logging to the same bucket creates a feedback loop (the log write itself generates a log entry). A dedicated logging bucket keeps access logs clean and separate from application data.
